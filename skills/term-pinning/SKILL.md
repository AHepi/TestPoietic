# Term Pinning (Reed W1)

<!-- PROMPT-CORE-BEGIN -->
A pin is a clause fitted to a battery, never to an intuition.

1. Read the battery first. If no battery file exists for the term, stop
   and say so; pinning without a battery is imagination, not analysis.
2. Draft the candidate clause in the fragment language, citing the exact
   parent anchors by file and hash prefix.
3. Check the clause against EVERY battery member, in writing:
   - each positive: derive admission, line by line;
   - each near-miss: derive exclusion, naming the conjunct that does it;
   - each boundary/OPEN case: state what the clause says and whether the
     OPEN question survives.
4. Check the risk corridor walls explicitly: the too-weak wall must now
   be excluded, the too-strong wall must now be admitted. If either
   check fails, the clause is wrong; revise and re-check the WHOLE
   battery, not just the failed member.
5. State the two-sided check: exhibit (or name) one structure satisfying
   the clause and one failing it, both inside the declared class.
6. Non-claims are mandatory: list what the pin does NOT do (no row
   discharged, no count moved, no sealed byte edited).
7. Output only files inside the task cone, in the driver format.
